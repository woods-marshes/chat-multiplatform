## 二、P0 — 立即修复

### P0-1 [Critical] 文章编辑器在无协作文档下完全不可用
`features/article-editor/src/jvmMain/.../TiptapEditorWebView.kt:215`
（androidMain `:189`、wasmJsMain `:190` 同样问题）

```kotlin
"window.__editorShell.initialize(" +
    "decodeURIComponent(escape(window.atob(\"$titleB64\"))), " +
    "decodeURIComponent(escape(window.atob(\"$jsonB64\")));"   // ← 少一个 )
```

括号计数：发出 `initialize(decodeURIComponent(escape(window.atob("T"))), decodeURIComponent(escape(window.atob("J")));`，
净深度为 3 而非 0 → **SyntaxError**。上方 collab 分支（`:213`）是正确的一行。
`collabUrl == null || roomId == null` 时 `initialize` 永不执行，`evaluateJavaScript` 的返回值被丢弃，
所以异常完全静默：编辑区一直空白直到 10 秒超时才显示 "Editor initialization timed out"。

**修复**：抽出统一的 `jsCall` 构造器，保证括号平衡；为生成的 JS 字符串写一个括号平衡单测（这类 bug 一测即中）。
顺带把 collab 分支已有的 `collabJsonStr` 序列化复用到非协作者路径，避免两条分支再次分叉。

### P0-2 [Critical] 明文密码写入生产日志
`features/auth/src/commonMain/.../AuthViewModel.kt:70`

```kotlin
log.info { "[AuthViewModel]: s -> $s" }
```

`AuthState.kt:21-22` 中 `password` / `confirmPassword` 是 `data class` 成员，`toString()` 全量输出。
每次登录/注册成功都会在 INFO 级别落盘密码。Android 侧可被 `adb logcat` 读取，桌面侧会写入轮转日志文件并随缺陷报告外发。

**修复**：删除该行，或只记录 mode + email。原则：**绝不记录承载密钥的 state 对象**；
若需保留字段，应将凭据拆到独立 holder 并实现脱敏 `toString`。

### P0-3 [Critical] Web 端数据库是纯内存的，缓存每次刷新即清空
`core/database/src/webMain/.../DatabaseModule.web.kt:14`

```kotlin
return createDefaultWebWorkerDriver().also { ...; schema.create(it).await() }
```

`createDefaultWebWorkerDriver()` 加载的 `@cashapp/sqldelight-sqljs-worker` 内部只做 `new SQL.Database()`，
**没有任何 IndexedDB / OPFS 持久化代码**；`WebWorkerDriver.close()` 即 `worker.terminate()`，整个库被销毁。
而 `DatabaseHolder.closeLocked()`（`DatabaseModule.kt:208`）在每次切换用户与登出时都会 `close()`。

后果：js/wasmJs 上「离线优先」完全是假的——每次刷新页面 / 登出缓存全部丢失；
传入的 `dbName = "chat_${userId}.db"`（`:170`）被直接丢弃，多用户共用同一个临时库。

**修复**：二选一——要么直接砍掉 js/wasmJs 目标并像 `RoomDatabaseModule` 那样 fail-fast；
要么换成带持久化的 web driver 并让 `dbName` 真正作为 key。**不要在离线缓存实际不可用的前提下继续声称 web 目标可用。**

### P0-4 [Critical] SQLDelight 事务体内读操作会跨线程跳出事务
`core/database/src/commonMain/.../session/DatabaseSessionGate.kt:254`

```kotlin
val value = withContext(ioContext.minusKey(Job)) {   // ← 线程切换
    extractor(query)
}
```

`JdbcSqliteDriver` 的 `ThreadedConnectionManager` 把事务/连接保存在 `ThreadLocal`（`JdbcDriver.kt:109-128`），
因此在 IO 线程上 `transaction == null`、`getConnection()` 返回**另一个连接**。

当前可达路径：`OfflineFirstMessageRepositoryImpl.kt:517-533` 在 `messageDao.transaction { }` 内部调用
`conversationDao.getConversationById(...).firstOrNull()` 和 `participantDao.insertParticipant(...)`，
线程切换发生在事务体中途 → 所谓的「原子 merge」可能部分提交、读到事务前旧状态，或在第二个写入者上 `SQLITE_BUSY`。
`notifyQueries` 也会在同一时刻因 `currentTransaction()` 为 null 而提前触发。

> Android 侧（`AndroidSqliteDriver` 单一 `SupportSQLiteDatabase`）行为**待验证**；JVM/桌面路径已确认。

**修复**：事务体必须保持线程亲和性——为事务内使用提供同步的 `Query`-based 读取helper，
或让 `transaction {}` 把整个 body 派发到单一 dispatcher 并禁止内部 `withContext`。
同时让 `MessageDaoImpl.transaction` 与 `ContactDaoImpl.transaction:61-68` 对称地用 `BoundDatabaseElement` 包裹。

## 六、系统性问题（比单个条目更值得修）

1. **i18n 存在结构性绕过**，不是零星遗漏。`LyricistSetup.getLocaleStrings()` 硬编码 + `TimeUtils`/`RelativeTimeUtils` 不读 `LocalStrings`（时间戳永远中文）、`AuthState` 校验器、11 条 WebView 文案、`AudioBubble`/`VideoBubble`/`UserAvatar` 无障碍描述、`ArticleDetailViewModel` 的 `e.toString()`、以及全部 `ConversationApi`/`ContactApi` 的失败布尔。
   **同一句话在 4 个平台的 actual 里各写一遍**（article / article-editor 的 WebView 组件），是重复的直接成因。修法：把这些字符串收进 `Strings`，由 common 层的 `expect` 暴露，让 actual 不再自带文案。

2. **"声明了但没人验证"**：`core:datastore` / `core:model` / `core:domain` 零测试文件；`core:database-room` 零测试且无与 SQLDelight 的 schema 一致性检查；`features/*` 无 bridge 生成字符串测试；`desktopApp`/`webApp` 无 test 源集。`core:database` 唯一分页测试用 `IN_MEMORY`（`StaticConnectionManager` 路径），而真实桌面应用走的是文件型 `ThreadedConnectionManager`——P0-4 正好在这个盲区。

3. **凭据存储缺少统一收口**。当前散落在 4 个 `actual` 中，行为各不相同：Web 用 `localStorage`（可被任意脚本读取）、Android 用 `filesDir`（进备份）、桌面用明文文件（默认权限）、DataStore 无 corruption handler。**正确形态是让服务端下发 `HttpOnly` + `Secure` + `SameSite` cookie，客户端只在内存里持短生命周期 access token**；这是唯一能一次性解决 P1-1/2/3/4 与 P2「Web 登出残留」的结构性方案。

4. **`INSERT OR REPLACE` 与 `Boolean` 状态码这两个"看似安全的惯例"在此项目中都是陷阱**：前者会级联删除消息历史（P1-13 附近），后者在 `expectSuccess = true` 下把 2xx-非-200 的成功静默转成失败。建议加进 lint / review checklist。

5. **同款代码按平台复制而非抽象**，直接产生了 P1-15 / P1-16 / P1-19 / P2-5 / P2-6 这一整族问题：jvm actual 有正确错误处理而 android/wasmJs 没有；media bubble 的 `isOwnMessage` 分支三个组件有两个漏了。WebView 资源准备、失败态、加载态应该抽到 common 层共用。

6. **`core:network-api` 用 `api(core.model)` 把客户端领域模型当线缆契约**，让 UI 改动静默改变 REST 与 protobuf 格式（P1 区域 network 第 6 条）。这是唯一一处"编译器无法察觉的接口变更"，风险等级应等同于数据库 schema 变更。
